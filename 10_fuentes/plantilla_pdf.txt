                                       Introducción



La seguridad de un sistema operativo depende en gran medida de la forma en que se
encuentran configurados sus servicios, permisos, mecanismos de autenticación y componentes
internos. Una instalación que mantiene configuraciones innecesarias, servicios habilitados sin
requerimiento o políticas de seguridad poco restrictivas puede incrementar su exposición
frente a amenazas. Por esta razón, el hardening constituye una práctica fundamental dentro
de la administración segura de sistemas, ya que busca fortalecer el entorno operativo mediante
la aplicación de configuraciones orientadas a reducir riesgos y limitar posibles vectores de
ataque.

En el presente laboratorio se realizará un proceso de endurecimiento sobre un sistema Ubuntu
24.04 LTS con arquitectura ARM64, utilizando como referencia las Security Technical
Implementation Guides (STIG) y contenido basado en Security Content Automation
Protocol (SCAP). Estas tecnologías permiten evaluar el nivel de cumplimiento de
determinadas configuraciones de seguridad y facilitan la identificación de controles que
requieren ser revisados o corregidos. Asimismo, mediante una herramienta de evaluación
compatible con SCAP se realizará un análisis inicial del sistema con el propósito de obtener
un reporte de su estado antes de aplicar las medidas de hardening.

A partir de los resultados obtenidos se seleccionarán diferentes controles de seguridad que
presenten incumplimientos, los cuales serán analizados y corregidos de acuerdo con las
recomendaciones correspondientes para Ubuntu. Posteriormente, se efectuará una nueva
evaluación para verificar los cambios realizados y comparar el estado del sistema antes y
después del proceso de endurecimiento. De esta manera, el laboratorio permitirá observar de
forma práctica cómo la aplicación de controles de seguridad puede contribuir a mejorar la
configuración de un sistema Linux y reducir su superficie de ataque.

              Figura 3. Comprobación de la arquitectura mediante uname -m




Se verificó específicamente la arquitectura del sistema mediante el comando uname -m. Este
comando consulta la arquitectura de hardware reconocida por el kernel y devuelve su
denominación correspondiente. El resultado obtenido fue x86_64, lo cual confirma que el
sistema utiliza una arquitectura de 64 bits perteneciente a la familia x86. Esta comprobación
es especialmente relevante para el desarrollo del laboratorio, debido a que inicialmente se
consideró utilizar herramientas destinadas a ARM64; sin embargo, la evidencia obtenida
demuestra que el equipo corresponde realmente a una plataforma x86-64/AMD64. Por esta
razón, las versiones de SCAP Compliance Checker y demás herramientas que requieran
seleccionar una arquitectura deberán descargarse en su variante para sistemas x86 de 64 bits.
El resultado también coincide con la arquitectura x86-64 presentada anteriormente por
hostnamectl. La utilización de uname -m proporciona así una comprobación directa e
independiente de esta característica del sistema. Con ello se garantiza que las herramientas
utilizadas posteriormente sean compatibles con el hardware sobre el cual se realizará el
hardening.

del kernel, módulos cargados o configuraciones de seguridad específicas. El resultado

     4.​ Cuestionario



     ●​ ¿Cuál es la función del módulo pam_faildelay y por qué es importante en la
        seguridad de la autenticación?

        La función principal de pam_faildelay es introducir un retardo de tiempo configurable,
        por ejemplo, 4 segundos, entre intentos fallidos de autenticación en el sistema. Es
        fundamental para la seguridad porque mitiga los ataques de fuerza bruta y ataques
        basados en diccionario, ya que ralentiza drásticamente la capacidad de un atacante
        para probar contraseñas de forma automatizada o continua, reduciendo la posibilidad
        de vulnerar cuentas locales o remotas.




     ●​ ¿Qué riesgos implica dejar habilitado el acceso directo a la cuenta root vía SSH o
        inicio de sesión local?

        Permitir el inicio de sesión directo con root implica exponer la cuenta con máxima
        autoridad del sistema como un objetivo directo de autenticación. El riesgo radica en
        que un atacante solo necesita descubrir o vulnerar la contraseña de un nombre de
        usuario predeterminado y universalmente conocido, obteniendo control administrativo
        total e inmediato. Al deshabilitarlo y utilizar cuentas de usuario nominativas con
        escalado mediante sudo, se facilita la auditoría individual y la identificación de quién
        ejecutó cada comando privilegiado.




     ●​ ¿Por qué es importante restringir el acceso al buffer de mensajes del kernel
        (kernel.dmesg_restrict = 1)?

        Es importante porque el buffer de mensajes del kernel (dmesg) contiene información
        sobre eventos de bajo nivel del sistema operativo, memoria, fallos y hardware. Si
        usuarios sin privilegios pueden consultar esta información, un atacante podría obtener
        datos útiles para identificar vulnerabilidades, conocer direcciones de memoria o
        recopilar información de depuración que facilite ataques de escalada de privilegios.

     ●​ ¿Cuál es el propósito de configurar la directiva UMASK 077 por defecto en el
        sistema?

        El propósito de utilizar una máscara de permisos restrictiva como UMASK 077 es
        conseguir que los archivos y directorios creados por un usuario sean accesibles
        únicamente por su propietario, sin permisos para el grupo ni para otros usuarios. Esto
        ayuda a proteger información confidencial y evita que otros usuarios o procesos
        locales puedan acceder, modificar o leer archivos privados.




     ●​ ¿Por qué se exige la sincronización horaria precisa mediante servicios como
        Chrony en entornos con estándares STIG?

        Mantener la hora sincronizada mediante servicios como Chrony es indispensable para
        la integridad de los registros y la auditoría. Si los relojes de los sistemas presentan
        diferencias importantes, resulta difícil correlacionar eventos de seguridad y reconstruir
        correctamente una línea temporal durante una investigación. Además, una hora
        incorrecta puede afectar a la validación de certificados digitales, tokens de
        autenticación y otros mecanismos que dependen de la fecha y hora del sistema.
